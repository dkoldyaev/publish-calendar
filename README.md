# Календарь публикаций фотографий (Offline-First Photo Publishing Scheduler)

Персональное прогрессивное веб-приложение (PWA) и серверный API для планирования ежедневной ручной публикации фотографий с полной поддержкой офлайн-работы, детерминированным расписанием, синхронизацией с оптимистичным контролем конкурентности, адаптерами хранения бинарных данных (локальное файловое хранилище или S3-совместимое объектное хранилище, выбираемое через `STORAGE_DRIVER`) и напоминаниями через Web Push.

## 2. Доменная модель планирования (Core Scheduling Model)

### Жизненный цикл фотографии
Каждая фотография находится в одном из трёх состояний:
- `pending` — находится в активной упорядоченной очереди ожидания публикации.
- `published` — терминальное состояние подтверждённой публикации (сохраняется в истории и отображается в календаре за фактическую дату подтверждения).
- `deleted` — терминальное состояние удалённой фотографии (исключается из очереди и будущего расписания).

### Правила расчёта расписания (`calculateSchedule`)
Назначенные даты публикации являются **чистой детерминированной проекцией** состояния очереди, а не мутируемым полем каждой фотографии:
1. **Инвариант «одно фото в день»**: на один календарный день в выбранном часовом поясе IANA назначается не более одной ожидающей (`pending`) фотографии.
2. **Подтверждение в день публикации (Same-Day Confirmation)**: если фотография подтверждена как опубликованная в текущий локальный день `todayLocal`, этот день считается занятым выполненной публикацией, а следующая ожидающая фотография остаётся назначенной на следующий день (`todayLocal + 1`).
3. **Раннее подтверждение (Early Confirmation)**: если пользователь досрочно подтверждает публикацию фотографии сегодня, сегодняшний день помечается как уже содержащий подтверждённую публикацию, поэтому другие ожидающие фотографии не назначаются на этот же календарный день.
4. **Пропущенная публикация (Missed Publication)**: если день завершился без подтверждения публикации, при наступлении следующего календарного дня в часовом поясе пользователя первая фотография очереди автоматически переносится на новый текущий день, а все последующие фотографии сдвигаются на 1 день вперёд. Прошедший день без публикаций при наличии ожидавших в очереди фотографий отмечается в календаре статусом **«Пропущено» (`missed`)**.
5. **Позднее подтверждение (Late Confirmation)**: подтверждение пропущенной фотографии фиксирует её публикацию за фактическим текущим днём подтверждения и сдвигает оставшуюся очередь на последующие дни.
6. **Удаление (Deletion)**: удаление ожидающей фотографии закрывает образовавшийся промежуток в очереди без нарушения правила «одно фото в день».
7. **Изменение порядка (Reordering)**: перетаскивание (drag-and-drop) или перемещение кнопками с клавиатуры/сенсорного экрана меняет позиции `0..N-1` только для `pending` фотографий и мгновенно пересчитывает проекцию будущих дат, не затрагивая исторические записи.
8. **Отсрочка (Postponement)**:
   - Короткая отсрочка (`+15 мин`, `+1 час`, `+3 часа`, `+6 часов`) изменяет только время следующего напоминания (`activePostponedRemindAt`) для текущей фотографии, не меняя назначенный календарный день публикации.
   - Отсрочка **«На завтра» (`tomorrow`)** устанавливает `postponedUntilDate = tomorrowLocal` и переносит саму дату публикации первой и всех последующих ожидающих фотографий на 1 календарный день вперёд.
9. **Часовые пояса и переходы на летнее/зимнее время (DST)**: расчёт локальных дат (`YYYY-MM-DD`) и перевод локального времени напоминания (`HH:MM`) в UTC выполняются с использованием базы часовых поясов IANA (`Intl.DateTimeFormat`), корректно обрабатывая 23-часовые и 25-часовые сутки при переходах DST.

## 3. Поддерживаемые форматы файлов и обработка ZIP-архивов

На экране загрузки поддерживается одновременный выбор отдельных изображений и одного или нескольких `.zip` архивов:
- **Поддерживаемые форматы изображений**: `JPEG` (`.jpg`, `.jpeg`), `PNG` (`.png`), `WebP` (`.webp`), `GIF` (`.gif`), `AVIF` (`.avif`).
- Каждый файл проверяется как по расширению, так и по бинарной сигнатуре заголовка (magic bytes).
- **Безопасная распаковка ZIP-архивов**:
  - Защита от обхода путей (`Path Traversal`, `../`, абсолютные пути).
  - Защита от ZIP-бомб: проверка коэффициента сжатия (`MAX_ZIP_EXPANSION_RATIO`), максимального объёма распаковки (`MAX_ZIP_EXTRACTED_BYTES`) и числа записей (`MAX_ZIP_ENTRIES`) **до** распаковки содержимого в память.
  - Автоматический обход вложенных директорий, пропуск системных метаданных (`__MACOSX`, `.DS_Store`) и детерминированная дедупликация совпадающих имён файлов (`photo.jpg` -> `photo (2).jpg`).
  - Ошибка валидации одного файла отображается в отчёте по файлам и не отменяет импорт остальных корректных фотографий пакета.

## 4. Офлайн-архитектура и разрешение конфликтов синхронизации

- **Локальное хранилище**:
  - Метаданные фотографий, бинарные данные изображений (`Uint8Array` в `photo_blobs`), очередь операций синхронизации (`sync_queue`) и настройки хранятся в **IndexedDB**. `localStorage` для бинарных данных не используется.
  - Приложение запрашивает `navigator.storage.persist()` и обрабатывает `QuotaExceededError`.
  - В разделе «Настройки» доступна безопасная очистка локального кэша бинарных файлов, которая удаляет локальные копии **только** тех фотографий, чьё сохранение в удалённом хранилище S3 (`uploadState = 'uploaded'`) подтверждено сервером и по которым нет ожидающих операций синхронизации.
- **Правила разрешения конфликтов (Optimistic Concurrency Control)**:
  - Все мутации снабжаются `idempotencyKey` (UUID) и базовым номером ревизии (`baseRevision` / `baseQueueRevision`).
  - Терминальные состояния (`published`, `deleted`) имеют приоритет над состоянием `pending`.
  - При конфликте между `published` и `deleted` на разных устройствах приоритет всегда имеет `published`, чтобы подтверждённая публикация никогда не была потеряна.
  - При параллельном редактировании описания одной фотографии на двух устройствах создаётся запись `DESCRIPTION_CONFLICT` (`MANUAL_REQUIRED`), позволяющая пользователю в интерфейсе выбрать нужный вариант без потери текста.
  - При параллельном изменении порядка очереди (`REORDER_QUEUE`) выполняется детерминированное слияние порядка (`QUEUE_REORDER_MERGED`) без дублирования или потери новых фотографий.

## 5. Особенности и ограничения Web Push в браузерах и ОС

- Уведомления доставляются через стандартный Web Push протокол (RFC 8030 / RFC 8291 / RFC 8292 VAPID) и обрабатываются Service Worker (`sw.js`).
- **Ограничения платформ**:
  - **iOS / iPadOS (Safari)**: Web Push поддерживается начиная с iOS 16.4 **только** после установки PWA на экран «Домой» («Поделиться» -> «На экран „Домой“»).
  - **Кнопки действий в уведомлениях (`NotificationAction`)**: поддерживаются в Chromium-браузерах на Android и настольных ОС, но могут не отображаться в Safari и Firefox. Если браузер не отображает кнопки действий на самом баннере уведомления, клик по уведомлению открывает экран карточки фотографии (`/photo/:id?from=notification`), где все 5 вариантов отсрочки (`+15 мин`, `+1 час`, `+3 часа`, `+6 часов`, `На завтра`) доступны непосредственно в интерфейсе приложения.
  - Для получения Push-уведомлений устройство должно иметь подключение к сети. Работа самого приложения в офлайн-режиме не зависит от доставки Push-уведомлений.

## 6. Политика конфигурации (Strict Environment-Only Policy)

Все параметры среды выполнения задаются **исключительно** через переменные окружения. Скрытые значения по умолчанию в коде и Docker Compose отсутствуют. Полный перечень переменных с описанием назначения и формата приведён в файле [`.env.example`](file:///workspace/publish-calendar/.env.example).

При отсутствии, пустом значении или неверном формате любой обязательной переменной приложение немедленно завершает запуск с ошибкой `ConfigurationError: <VARIABLE> ...` до начала приёма HTTP-запросов или запуска фоновых задач.

Подготовьте файл `.env` на основе `.env.example`:
```bash
cp .env.example .env
# Заполните секреты AUTH_SECRET, AUTH_DEFAULT_ACCESS_CODE, POSTGRES_PASSWORD, VAPID_*,
# а также выберите драйвер хранения STORAGE_DRIVER=local (с LOCAL_STORAGE_DIR) или STORAGE_DRIVER=s3 (с S3_*)
```

## 7. Развёртывание в Docker Compose (Dokploy и локальный запуск)

### Режим 1: Промышленное развёртывание (Dokploy со встроенным Traefik + внешний PostgreSQL)

В базовом [`docker-compose.yml`](file:///workspace/publish-calendar/docker-compose.yml) определены только сервисы приложений (`api` и `web`) **без секций `ports` и без локального прокси-сервера**, так как в продакшн-среде (Dokploy) проксированием трафика к контейнерам занимается встроенный в платформу Traefik:

```bash
docker compose -f docker-compose.yml up -d --build
```

### Режим 2: Локальный запуск (через `docker-compose.override.yml`)

Файл `docker-compose.override.yml` предназначен исключительно для локальной разработки и добавлен в `.gitignore`. В репозитории хранится шаблон [`docker-compose.override.yml.example`](file:///workspace/publish-calendar/docker-compose.override.yml.example), который добавляет:
- локальный реверс-прокси `traefik` (`traefik:v3.2`), маршрутизирующий `/api` на `api:${API_PORT}` и `/` на `web:${WEB_PORT}` через Docker labels;
- локальный контейнер `postgres` (`postgres:16-alpine`) с постоянным томом `postgres_data`;
- секции `ports` для локального проброса портов контейнеров на хост-машину.

Для локального запуска скопируйте шаблон и запустите стек:

```bash
cp docker-compose.override.yml.example docker-compose.override.yml
docker compose -f docker-compose.yml -f docker-compose.override.yml up -d --build
```
